# План улучшения прогноза для WB Space

Дата: 9 ноября 2026 года.

Цель — улучшить текущий результат 0,330–0,331 до значения ниже 0,323. Это целевой результат, а не обещание качества. Контроль — stepa330: CatBoost recent75, профиль profile28 на h2–h8 и аддитивная поправка.

Работаем по циклу: ассистент готовит ноутбук → Матвей запускает его на Kaggle и сохраняет результаты → ассистент анализирует результаты → готовим следующую волну. Будущие ноутбуки уточняем после проверки предыдущих результатов.

## Порядок запусков

| Этап | Ноутбук | Задача | Зависимость |
| --- | --- | --- | --- |
| 0 | 00_baseline.ipynb | Воспроизвести контроль и собрать прогнозы временных проверок | Запускается первым |
| 1А | 01_calibration.ipynb | Проверить адаптивную калибровку | После проверки этапа 0 |
| 1Б | 02_total_volume.ipynb | Прогноз общего объёма и согласование маршрутных прогнозов | Параллельно с 1А и 1В |
| 1В | 03_windows_features.ipynb | Окна обучения и дополнительные признаки | Параллельно с 1А и 1Б |
| 2 | 04_losses.ipynb | Сравнить функции потерь на выбранных окне и признаках | После разбора первой волны |
| 3 | 05_ensemble.ipynb | Объединить победителей и собрать итоговый submission | После остальных экспериментов |

Всего: один подготовительный и пять экспериментальных ноутбуков. Сейчас готов только 00_baseline.ipynb; остальные имена обозначают запланированные файлы.

## Этап 0 — контроль

Ноутбук [00_baseline.ipynb](00_baseline.ipynb) автономен: код репозитория на Kaggle загружать не требуется.

Действия Матвея:

1. Импортировать ноутбук в Kaggle.
2. Подключить dataset с train_solo_track.parquet и test_solo_track.parquet.
3. Включить GPU. По умолчанию GPU_DEVICES='0'; CPU fallback отключён.
4. Выполнить Save Version → Save & Run All.
5. Сохранить выполненный ноутбук, results.zip и models.zip.

Что делает ноутбук:

- Воспроизводит фиксированную конфигурацию победителя stepa330, без повторного поиска режима.
- Отдельно показывает старую проверку legacy: обучение до 4 октября, tuning 4–17 октября, holdout 18–31 октября для текущих данных.
- Собирает weekly-прогнозы шести недель с еженедельным переобучением. 20 сентября – 3 октября — warmup калибровки; 4–17 октября — tuning; 18–31 октября — ранее просмотренный holdout. Даты вычисляются из данных.
- Для weekly использует фиксированные 1500 деревьев без early stopping по будущей неделе. Контрольная поправка оценивается по warmup и фиксируется до tuning.
- Обучает 64 модели на GPU: 8 legacy, 48 weekly, 8 финальных. Признаки обрабатываются по одному горизонту.
- Сохраняет прогнозы всех горизонтов, параметры, временные границы, метрики, важности, время работы, агрегированную историю и контрольный submission.

После каждой модели сохраняются файлы результатов и results.zip; после горизонта — checkpoint.zip с моделями. Для продолжения в той же файловой системе достаточно Run All. Для новой сессии нужен checkpoint.zip: распаковать в /kaggle/working с сохранением папки baseline_00 и запустить с прежними настройками. Альтернативный способ через RESTORE_DIR описан в ноутбуке. Незавершённая модель обучается заново; завершённые пропускаются. Данные, версии и контрольные суммы проверяются.

После получения результатов ассистент проверяет воспроизводимость контроля, полноту панелей, временные границы и расхождения метрик. Затем готовит первую параллельную волну.

## Первая волна — три независимых эксперимента

### Калибровка

01_calibration работает на сохранённых прогнозах без переобучения базовых моделей. Сравниваем текущую фиксированную поправку с поправкой по последним 7, 14 и 28 дням, силу коррекции 50% и 100%. Для каждого дня используются только ранее доступные ответы. Настройки выбираются на tuning и фиксируются перед последующей проверкой.

### Общий объём

02_total_volume строит отдельный прогноз суммы по всем маршрутам из утренних таргетов, статусов и сезонных профилей. Сравниваем отсутствие согласования, частичное и полное согласование суммы маршрутных прогнозов с прогнозом общего объёма. Сначала проверяем эффект отдельно от адаптивной калибровки.

### Окно обучения и признаки

03_windows_features выполняет два последовательных шага:

1. При одинаковых признаках сравнивает текущие последние 75% истории с фиксированными окнами 42, 56 и 70 дней.
2. На выбранном окне отдельно проверяет признаки соседних исторических слотов и пиков, затем признаки нагрузки сети. Основное внимание — h3–h8.

Окно и признаки выбираются только на периодах подбора. Все три ноутбука используют одинаковые контроль, даты и метрики.

После первой волны ассистент составляет таблицу эффектов: качество, устойчивость по неделям, изменение WAPE и bias, стоимость по времени. По ней фиксируется конфигурация следующего этапа.

## Вторая волна — функция потерь

04_losses сравнивает MAE, Quantile с alpha=0,55 и 0,60, RMSE на выбранных окне и признаках. Обучение CatBoost — на GPU.

Каждый вариант оценивается до и после одинаковой процедуры калибровки. Выбор проводится по полной конкурсной метрике на tuning, с последующей проверкой переноса.

## Третья волна — ансамбль и submission

05_ensemble сравнивает лучшую одиночную модель с небольшими смесями победителей. Дополнительно проверяется совместное применение адаптивной калибровки и коррекции общего объёма. Другие модели проекта включаются только при наличии сопоставимых проверочных прогнозов.

После фиксации настроек оцениваем последующий период, переобучаем нужные модели на доступной истории и создаём submission. Результат на WB оценивается отдельно от локальных метрик.

## Общие правила оценки

- Основной локальный критерий — средняя дневная WAPE + |Relative Bias| по всем маршрутам и восьми горизонтам вместе.
- Дополнительно считаем pooled score по объединённым строкам, WAPE и signed bias отдельно.
- Смотрим результаты по неделям, горизонтам и субботам; не подменяем общий дневной score средним score отдельных горизонтов.
- Все обучающие метки и статистики должны быть доступны до соответствующей границы. Признаки проверочного дня могут использовать наблюдения до его cutoff 10:30.
- Выбор настроек проводится до следующего оценочного периода. Последние 14 дней уже изучались в проекте и не являются новым слепым тестом.
- Предпочитаем улучшения, которые переносятся между временными окнами. При малой и нестабильной разнице сохраняем более простой вариант.
- Финальные модели переобучаются после оценки. Метрики до refit и после refit не смешиваются.

## Сохранение и передача результатов

Для каждого эксперимента сохраняем выполненный .ipynb с выводами, results.zip и архив моделей, если было обучение. Для восстановления незавершённого baseline нужен checkpoint.zip, а не results.zip.

В results.zip должны быть прогнозы с ключами cutoff, route_id, horizon и фактом y для исторических дат, метрики, параметры, границы обучения, идентификатор запуска и тайминги. Одного submission или скриншота метрик недостаточно.

Результаты разных запусков складываем в отдельные папки, например matvey/results/00_baseline/run_01/. Не перезаписываем предыдущие результаты до их разбора. Ассистент читает сохранённые файлы, сообщает выводы и готовит следующий этап.

# Контроль очистки: raw против clean, обучение на train + val перед test

Импортируйте `xgb_clean_vs_raw.ipynb` в Kaggle, подключите `train_solo_track.parquet`, включите GPU и выполните Run All один раз. Обучение запускает пользователь. Для GPU-матриц требуется установленный CuPy. Файл конкурсных запросов не требуется: этот ноутбук предназначен для локального сравнения, без сабмитов.

Варианты `raw` и `clean` оба используют все получасовые старты и восемь отдельных моделей h1–h8. Их параметры, количество деревьев, seed и набор колонок одинаковы; значения встроены из `best_params/best_params.json`, секция `refit_params`. Подбора параметров XGBoost и early stopping нет.

Raw сохраняет исходную цель и все статусы. Clean использует прежний причинный MAD-4 фильтр в log1p: медиана и MAD предыдущих 28 дней того же получасового слота, минимум 14 наблюдений; масштаб max(1.4826 × MAD, 0.25), порог 4; замена медианой. Очистка выполняется до построения признаков. Метрики и калибровка всегда используют исходные ответы.

## Протокол

1. Train — до 7 октября 2025 года. На всех получасовых стартах обучаются по восемь моделей каждой ветки. Прогнозируется val 7–24 октября, только старты 10:30; test ещё не прогнозируется.
2. На val сравниваются none, global, grouped и nonlinear. Для fit используется 7–15 октября, для выбора типа по WAPE + |Relative Bias| — 16–24 октября. Квинтили маршрутов берутся из общей исходной train-истории. Коэффициенты выбранного типа переоцениваются по всем OOS-прогнозам val и исходным val-ответам.
3. Калибровки фиксируются. Все 16 моделей заново обучаются на train + val: все доступные получасовые старты с timestamp метки строго раньше 25 октября. Корреляционные словари переоцениваются отдельно для raw и clean только на train + val. Число деревьев остаётся фиксированным.
4. На test 25–31 октября, старты 10:30, считаются WAPE, |Relative Bias| и их сумма до калибровки и после выбранного метода. Есть также средняя дневная метрика. Сравниваются одинаковые пары cutoff/route/horizon и исходные ответы.

Границы рассчитываются из входного датасета, указанные даты соответствуют текущему parquet. Октябрьский test уже использовался в проекте и не является новым слепым периодом. После каждого fit на первом этапе выводятся train/val и отметка об отложенной оценке test; после каждого fit на train + val — train/test. Выбор калибровки и гиперпараметров не использует test.

По последнему указанию пользователя независимая от выбора на val оценка test получается после переобучения на train + val, без включения test в fit. Полного переобучения на всей доступной размеченной истории нет. Сабмиты не создаются. Показатели этого опыта нельзя напрямую приписывать прежним моделям, обученным только на train: объём обучения изменён по запросу.

Калибратор обучен на OOS-прогнозах train-only моделей и переносится без изменения на модели train + val; возможное изменение смещения проверяется на test. В итоговой таблице есть также обе ветки без калибровки, чтобы оценить влияние очистки при одинаковой постобработке.

## Данные и модель на GPU

Для fit используется float32 CuPy-матрица и CuPy-цель на cuda:0. Она остаётся на GPU для расчёта train-прогноза, после чего освобождается. Val/test передаются как CuPy и прогнозируются через Booster.inplace_predict. На CPU возвращаются только предсказания для метрик/калибровки. Очистка, построение признаков и parquet остаются на CPU.

route_id кодируется по одному фиксированному справочнику routes и явно задаётся feature_types=c; прочие колонки — q. Порядок колонок, типы и названия сохраняются; route_encoding.csv содержит соответствие кодов. Это поддерживаемый [XGBoost способ работы с категориальными данными в NumPy/CuPy](https://xgboost.readthedocs.io/en/stable/python/examples/categorical.html).

Последовательно в GPU-памяти находится матрица одного горизонта одной ветки. В логах выводятся объём GPU-входов и свободная память до fit. Дополнительная память нужна внутренним структурам XGBoost. Используется одна GPU cuda:0, даже при двух T4; автоматического распараллеливания по двум GPU нет. Реальное ускорение и пиковое потребление VRAM требуют замера в Kaggle.

## Прогресс и файлы

В логах печатаются вариант, горизонт, этап TRAIN или TRAIN+VAL, число строк, максимальная timestamp обучающей метки, выбранная калибровка и длительность завершённого шага. Всего 32 fit: две ветки × восемь горизонтов × два этапа.

Артефакты лежат в `/kaggle/working/xgb_clean_vs_raw/runs/<запуск>/`:

- `comparison_trainval_test.csv` — главная сводка train + val/test до и после выбранной калибровки;
- `trainval_metrics_by_horizon.csv`, `test_metrics_by_day.csv` — разбор горизонтов и дней;
- `calibration_selection.csv`, `frozen_calibrators.json` — выбор только на val и фиксированные коэффициенты;
- `raw_test_predictions.parquet`, `clean_test_predictions.parquet`, `paired_test_predictions.parquet` — построчные результаты с исходными ответами;
- `raw_val_oos.parquet`, `clean_val_oos.parquet` — прогнозы для калибровки;
- модели обоих этапов, отчёт очистки, словари лагов, параметры, колонки, `final_protocol.json`.

Для анализа достаточно CSV/JSON/parquet из runs. Кэши признаков и модели для первого разбора можно не скачивать. Raw и clean имеют отдельные кэши; для переноса между сессиями подключите Output как Dataset, при необходимости задайте `CACHE_INPUTS` отдельно для каждой ветки.

Генератор: `.venv/bin/python scripts/build_xgb_clean_vs_raw_notebook.py`. Он читает текущие функции признаков/очистки из `xgb_cleaning.ipynb` и сохранённые параметры из best_params.

Локальная проверка выполняется без настоящего обучения и CUDA: с заглушками модели/CuPy проверены передача GPU-массивов, кодирование route_id и явный категориальный тип; дополнительно проверены компиляция ячеек, полный проход на реальной истории пяти маршрутов с заглушкой модели, проверка границ каждого из 32 fit, отсутствия test-прогнозов до фиксации калибровки, неизменности коэффициентов при train + val, исходных test-ответов, совпадения ключей и отсутствия полного refit/сабмитов. Реальные метрики появятся после запуска пользователем в Kaggle.

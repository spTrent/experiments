# Четыре Kaggle-ноутбука для стекинга

Подготовим **ровно четыре автономных `.ipynb`**. Каждый запускается из `Save & Run All` и отвечает за два горизонта. Первый ноутбук дополнительно получит режимы `assemble`, `evaluate` и `submit` для работы с результатами всех четырёх запусков. В текущем режиме планирования файлы ещё не созданы, обучение не запускалось.

## 1. Распределение вычислений

| Ноутбук | Горизонты | Работа в режиме `oof` |
|---|---|---|
| `stacking_part_1.ipynb` | h1, h8 | Все базы, три режима train, четыре OOF-недели |
| `stacking_part_2.ipynb` | h2, h7 | То же |
| `stacking_part_3.ipynb` | h3, h6 | То же |
| `stacking_part_4.ipynb` | h4, h5 | То же |

Четыре ноутбука генерируем из общего исходника, чтобы различия сводились к назначенным горизонтам и роли первого ноутбука. В каждый встраиваем проверенный снимок параметров его горизонтов. Для первого запуска достаточно подключить исходные train/test parquet и включить GPU. Каждый завершённый fit сохраняет прогнозы, метрики, время и идентификатор конфигурации. После прерывания ноутбук сможет продолжить работу из подключённого результата предыдущей сессии.

## 2. Базы, OOF и GPU

- **Три режима train.** `five_starts` использует старты 09:30–11:30 с шагом 30 минут. `mixed_starts` использует пять стартов в первые `floor(N / 4)` дат train и все получасы далее. `recent_all` пропускает те же первые даты и использует все получасы оставшегося периода. Граница четверти вычисляется внутри каждого fit. История для причинных лагов остаётся доступной.
- **30 глобальных прогнозов.** RF, LightGBM, CatBoost, XGBoost и Ridge в версиях direct/residual обучаются на каждом из трёх режимов. Используем все 80 проверенных конфигураций и сохранённое число деревьев. Параметры переносим на два новых режима без нового поиска.
- **Три прогноза маршрутных Ridge.** Для каждого режима одна колонка объединяет прогнозы 1000 маршрутов × 8 горизонтов. Исходные `alpha` выбирались на 4–17 октября, поэтому для OOF подберём их заново по 30 кандидатам на трёх недельных окнах до 20 сентября. Сохраним пакетный GPU-решатель, предобработку по маршруту и проверку нескольких решений против sklearn. Добавим один `profile28`. Получится **34 колонки прогнозов**.
- **Честный OOF.** Четыре недельных окна идут с 20 сентября по 17 октября. У каждой обучающей строки время целевой метки строго раньше начала прогнозируемой недели. Лаги, импутация и масштабирование рассчитываются по истории соответствующего фолда. Прогнозируем старт 10:30. После каждого fit выводим таблицу `train / отложенная неделя` с WAPE, знаковым Relative Bias и суммой `WAPE + |Relative Bias|`. Локальный test 18–31 октября остаётся закрыт до выбора метамодели.

| Модель | Бэкенд |
|---|---|
| XGBoost | CUDA, `tree_method='hist'`, с проверкой фактического устройства |
| CatBoost, включая метамодель | GPU |
| Random Forest | cuML на GPU, с параметрами исходного RF |
| LightGBM | Проверочный fit в начале сессии: сначала CUDA, затем GPU через OpenCL. Если оба недоступны, явно показать ошибку сборки и использовать CPU с записью в отчёт |
| Глобальная Ridge | GPU-решение Ridge с теми же train-медианами, стандартизацией, кодированием маршрутов, intercept и `alpha`. Обрабатывать матрицу блоками, сверить прогнозы с исходной sklearn Ridge |
| Маршрутные Ridge | Существующий пакетный решатель CuPy, с уменьшением размера пакета при нехватке VRAM |
| GatingNetwork / Weighted Average | PyTorch CUDA для сети, CPU-решатель линейного программирования для весов |

## 3. Сборка, сравнение и сабмит

1. **`assemble`.** Подключить четыре сохранённых результата к первому ноутбуку. Сборщик проверит **224 000 уникальных строк** по ключу `(route_id, cutoff, horizon)`, наличие всех 34 колонок, совпадение фактов, границы обучения и конечность прогнозов. Для недостающей части укажет конкретный горизонт, фолд, модель и режим.
2. **Сравнение.** Проверяем Weighted Average с неотрицательными весами суммой 1, CatBoostRegressor с поправкой к простому среднему и GatingNetwork с весами через `softmax`. Для каждого кандидата проверяем версии с тремя маршрутными колонками и без них. Последовательно обучаемся на неделях `1`, `1–2`, `1–3` и проверяем соответственно недели `2`, `3`, `4`. Выбираем по среднему трёх недельных значений конкурсной метрики. Сохраняем также оценки по неделям и горизонтам, простое среднее и лучший одиночный прогноз, выбранный на прошлом.
3. **`evaluate`.** После фиксации победителя четыре ноутбука строят прогнозы своих горизонтов на 18–31 октября. Первый собирает независимую таблицу `train / test` и сохраняет её до финального обучения. В отчёте прямо указываем, что **оценка test получена до переобучения на всей истории** и этот период уже изучался в проекте.
4. **`submit`.** Добавляем две октябрьские недели в OOF для финального обучения победившей метамодели. Первую неделю берём из оценки, для второй обновляем базы на истории до 25 октября. Затем каждый ноутбук переобучает нужные базы на всей доступной размеченной истории по соответствующему правилу train. Первый ноутбук собирает 8000 неотрицательных прогнозов в исходном порядке `id`.

## 4. Перепроверка и время

До передачи ноутбуков проверим синтаксис всех кодовых ячеек, отсутствие `assert`, комментариев и докстрингов, однократное распределение восьми горизонтов и точное совпадение встроенных параметров с оригиналами. На синтетической панели проверим три маски train, пограничные метки около полуночи, возврат сезонного уровня для residual, сверку Ridge с CPU и восстановление после прерывания. Сборщик проверим также на пропущенной и дублированной части. Обучение на реальной истории запустишь ты в Kaggle.

**Предварительный ориентир — несколько часов на параллельный OOF; для расписания я бы выделил сутки с возможностью продолжения.** В сохранённых логах выбранных trials пересчёт на четыре фолда *одного пятистартового режима* даёт ориентиры **0,80 / 0,45 / 0,46 / 0,46 часа** по четырём частям. Это пересчёт исторических длительностей, а не замер нового пайплайна. Наиболее неопределённые статьи — построение широких получасовых признаков, новый подбор маршрутных Ridge и фактический бэкенд LightGBM. Поэтому каждый ноутбук после первого полного фолда выдаст отдельные времена подготовки, подбора и fit, рассчитает ETA по оставшимся задачам и обновит её после каждого фолда. Общая длительность параллельного этапа определяется самой медленной частью.

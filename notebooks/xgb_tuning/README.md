# XGBoost: снижение WAPE на признаках stepa330

Для прямого сравнения исходной и очищенной истории на всех получасах используйте [xgb_clean_vs_raw.ipynb](xgb_clean_vs_raw.ipynb): калибровка выбирается на val, затем модели переобучаются на train + val и оцениваются на test. Полного refit с включением test и сабмитов нет. [Инструкция](CLEAN_VS_RAW_RUN.md).

Для нового запуска с очисткой исходного таргета и всех статусов, фиксированными лучшими параметрами, двумя режимами стартов и четырьмя калибровками используйте [xgb_cleaning.ipynb](xgb_cleaning.ipynb). Порядок запуска и протокол оценки описаны в [CLEANING_RUN.md](CLEANING_RUN.md).

[Ноутбук](xgb_tuning.ipynb) автономно запускается в Kaggle. Обучение — строго на NVIDIA GPU. До сборки признаков проверяются CUDA-сборка XGBoost и доступность устройства через драйвер. Переход XGBoost на CPU считается ошибкой. Построение признаков выполняется pandas/NumPy на CPU.

## Идея

Проверить восемь direct-моделей XGBoost на базовом наборе признаков из `notebooks/stepa/stepa330.ipynb`, с девятью обучающими стартами вокруг 10:30. По умолчанию оптимизируется MAE (`reg:absoluteerror`): на фиксированной выборке это соответствует минимизации WAPE. В первой ячейке можно заменить loss на `reg:squarederror` для контрольного запуска с тем же кэшем. Optuna подбирает конфигурацию только по MAE в исходных единицах таргета на val. Для фиксированной val-выборки минимум MAE эквивалентен минимуму WAPE: WAPE = MAE / mean(y). Bias и WAPE + |Relative Bias| выводятся для отчётности и не влияют на выбор.

В stepa330 победил режим recent75 с базовыми признаками. Перенесены формулы лагов, скользящих средних, статусов, календаря, сезонных профилей, утреннего уровня и корреляционного лага статуса 6. Экспериментальные peak/start-признаки h6 не входят в победивший набор и не добавлены. `profile28` теперь входит в XGBoost как дополнительный признак; `overlap` остаётся служебной колонкой и не входит в модель. Отсечение recent75, смешивание с profile28 и аддитивная калибровка не переносятся: здесь задано новое разбиение 80/20 и исследуется чистый XGBoost.

## Разбиение и оценка

- Последние семь дат, для которых доступны все цели 11:00–14:30, составляют test. Последний неполный день исходной истории не включается в оценку.
- Предыдущие полные прогнозные дни делятся хронологически: первые `floor(0.8 × N)` дней — train, остальные — val. Перемешивания нет.
- Train: 08:30, 09:00, 09:30, 10:00, 10:30, 11:00, 11:30, 12:00, 12:30. Для каждого старта цель находится через h × 30 минут, поэтому обучающие цели могут быть позже 14:30.
- Val/test: единственный старт 10:30; h1–h8 прогнозируют 11:00–14:30. Значение в 10:30 доступно модели как история.
- Метки train строго раньше полуночи первого val-дня. Корреляционный словарь оценивается только до этой границы, затем фиксируется для train/val/test и сохраняется в кэш.
- Исторические признаки каждой строки используют сведения не позже её старта. Следующий день val/test может использовать уже наблюдённые факты предыдущего дня: это последовательные ежедневные прогнозы.

На каждый горизонт выполняются ровно пять попыток: первая из `MANUAL_PARAMS`, ещё четыре предлагает Optuna TPE. Всего 40 обучений. `MANUAL_PARAMS_BY_HORIZON` в первой ячейке содержит восемь полностью выписанных независимых конфигураций с ключами 1–8. Меняйте значения в блоке нужного горизонта: например, `MANUAL_PARAMS_BY_HORIZON[6]` задаёт первую попытку для h6. Если удалить отдельный параметр из блока, он берётся из общего `MANUAL_PARAMS`. Настройки других горизонтов при редактировании одного блока не меняются. Ручная попытка допускает значения вне SEARCH_SPACE_BY_HORIZON[h]; она ставится первой через enqueue_trial, её параметры регистрируются в Optuna и сохраняются в итоговом JSON. Для ручных значений вне SEARCH_SPACE_BY_HORIZON[h] Optuna может вывести предупреждение о выходе за диапазон; значение сохраняется.

Early stopping использует MAE на val, а лучшая попытка выбирается только по MAE в исходных единицах таргета на val соответствующего горизонта. Общая метрика восьми горизонтов считается по объединённым прогнозам, а не усреднением восьми score. Независимый подбор восьми моделей не является совместной оптимизацией ансамбля. Дополнительно сохраняется средняя дневная метрика.

После каждого fit выводятся train/val. Test-метрики вычисляются для отчётности, но раскрываются общей таблицей только после фиксации всех победителей; они не используются в выборе. Итоговая таблица `all_trial_metrics.csv` содержит train/val/test для каждого из 40 обучений. Train оценивается на всех девяти стартах, val/test — только на центральном, поэтому состав выборок различается.

**Независимая от текущего подбора оценка test получена до переобучения на всей истории, моделями, обученными только на train.** Эти даты ранее изучались в проекте: это не новый слепой holdout. Ноутбук ограничен подбором и сохранением параметров, не делает финальный refit и submission. Перед будущей сборкой сабмита нужно переобучить все восемь моделей и корреляционный словарь на всей доступной размеченной истории, используя зафиксированное число деревьев.

## Запуск и перенос кэша

1. Импортировать `xgb_tuning.ipynb` в Kaggle и включить NVIDIA GPU в настройках Accelerator.
2. Подключить Dataset с `train_solo_track.parquet`. Путь определяется автоматически. Если копий несколько, указать `DATA_DIR` в первой ячейке. Файл соревнования test для подбора не нужен.
3. Задать ручную конфигурацию, при необходимости loss и выполнить Run All. Нужны CUDA-сборка XGBoost с поддержкой `device='cuda'` и `reg:absoluteerror`, Optuna, pandas, NumPy, PyArrow. Установка пакетов автоматически не выполняется.
4. Сохранить завершённую версию с Output. Для новой сессии сохранить папку `feature_cache` из Output как Kaggle Dataset и подключить его через Add Input.
5. Ноутбук автоматически найдёт совместимый `manifest.json` в `/kaggle/input`. Можно задать `CACHE_INPUT` как точный путь к папке с manifest и восемью parquet.

При повторном запуске с готовым кэшем не выполняются загрузка исходной панели в pandas, расчёт лагов, скользящих статистик и сборка признаков. Для проверки совместимости читаются SHA-256 исходного файла и кэшированных parquet — это последовательное чтение файлов, не пересчёт признаков. Кэш различает исходные данные, код признаков, старты, границы разбиения и настройки корреляционного лага. Гиперпараметры XGBoost не меняют кэш.

Каждый горизонт записывается атомарно; прерванная сборка в той же рабочей папке продолжится с отсутствующих горизонтов. Подключённый через CACHE_INPUT кэш должен быть полным и совместимым. В новой сессии без подключённого кэша признаки придётся построить заново: содержимое `/kaggle/working` не является постоянным хранилищем.

## Выходные файлы

Все результаты записываются под `/kaggle/working/xgb_tuning/`:

- `feature_cache/<fingerprint>/`: восемь parquet, проверки целостности, manifest и `status6_lags_train.csv`.
- `runs/<UTC-время>/best_params.json`: параметры восьми победителей, выбранное число деревьев, `val_mae`, порядок признаков, настройки преобразования цели, версии библиотек и границы разбиения.
- `best_h1.json` … `best_h8.json`: промежуточное сохранение победителя после каждого горизонта.
- `optuna.sqlite3`, `trials_h*.csv`: история поиска.
- `best_model_h*.ubj`: выбранные модели, обученные только на train. При загрузке учитывать `selected_trees`: в файле могут оставаться деревья после лучшей итерации early stopping.
- `best_predictions_h*_<split>.parquet`: прогнозы выбранных моделей в исходном масштабе, с отсечением отрицательных значений.
- `all_trial_metrics.csv`, `selected_metrics_by_horizon.csv`, `selected_metrics.csv`: отчёты всех попыток, выбранных горизонтов и объединённого прогноза.

Каждый новый запуск создаёт новую папку результатов и заново выполняет пять попыток на горизонт, используя существующий кэш. Автоматическое продолжение Optuna после прерывания в этом ноутбуке не реализовано.

## Проверка без обучения

Локально проверены схема ipynb, синтаксис, отсутствие assert/комментариев/докстрингов в коде, построение всех восьми горизонтов на искусственной панели, девять train-стартов, семь test-дней, временные границы, повторный вход в кэш без перезаписи и отказ от несовместимого подключённого кэша. Модели локально не обучались. GPU-обучение и фактическое качество проверяются пользователем в Kaggle.

## Расширение v2

Существующие входные признаки сохранены. Добавлены:

- `profile28` как вход direct-модели.
- Средние семи прошлых дней для целевого слота ±30/60 минут, разность крайних плеч, величина и положение максимума профиля. При равных максимумах выбирается самый ранний слот.
- Для статусов 1–3: отклонение текущего значения и среднего за 2 часа от нормы тех же получасов за предыдущие семь дней, отношение к норме и флаг малого знаменателя. Знаменатель ограничен снизу единицей в исходных единицах статуса; недоступная норма сохраняется как NaN.
- Лаги целевого слота 14/21/28 дней, разность недель 1 и 2, разность среднего последних трёх и предыдущих четырёх дней.
- Суммы по всей сети для таргета и статусов 1–3: текущий уровень, изменение за час, разность и отношение к норме за семь дней, флаг малого знаменателя, доля маршрута и её изменение за час. Для нулевой сетевой суммы доля остаётся NaN.

Все источники ограничены собственным cutoff строки. Сетевые признаки требуют полной панели маршрутов на момент прогноза. Новые нормировки используют только прошлые дни каждой строки, без статистик из будущего val/test. Сетевые суммы считаются один раз при сборке кэша.

Версия кэша — `stepa330_extended_xgb_9starts_v2`: для новых признаков требуется однократная пересборка. Если `CACHE_INPUT` указывает на старый кэш, сбросьте его в `None` перед первым запуском v2. Последующие запуски используют новый кэш. Цель Optuna остаётся MAE на val, обучение — строго GPU.

## Диапазоны поиска по горизонтам

В первой ячейке `SEARCH_SPACE_BY_HORIZON` содержит восемь независимых блоков границ всех восьми подбираемых параметров. Каждая пара — `(нижняя, верхняя)` граница. Функции `suggest_params_h1` … `suggest_params_h8` читают только блок своего горизонта; численные границы в функциях не зашиты. Ручные параметры первой попытки по-прежнему задаются отдельно в `MANUAL_PARAMS_BY_HORIZON`. Диапазоны и ручные параметры нужно редактировать независимо.

Начальная регуляризация изменена на 5%: для h1–h2 значения ручной попытки и обе границы `min_child_weight`, `reg_alpha`, `reg_lambda` умножены на 1.05; для h3–h8 — на 0.95. Например, ручной `reg_lambda` теперь 10.5 / 9.5 вместо 10.0. Остальные диапазоны и параметры сохранены. Это небольшое изменение исходных настроек, а не гарантия улучшения качества.

Каждый `best_h*.json` содержит использованный диапазон своего горизонта, а `best_params.json` — `search_space_by_horizon`. Кэш признаков от этих настроек не зависит.
